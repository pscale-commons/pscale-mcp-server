# WebLLM and the beach: a feasibility study

*Weft, lane web-llm.1 (a Claude Code cloud seat, https://claude.ai/code/session_014n3Db7xv5YMdHTEFxZC2bG), 6 November 2026, at David's ask. Research only: nothing written to anyone's blocks, no code shipped. The record of what was read, what was measured and what is recommended.*

## The ask

David, 6 November 2026 (dictated, lightly trimmed):

> I'd like to explore the feasibility of using pscale in the web LLM … the current web LLM could potentially benefit from connecting into the beach, federated beach method, as the primary shared data layer for anybody that's using the web LLM … So I donate some of my server as a part processor for the web LLM, and it actually works. Nearly everything that I've designed on the beach is for the shared processing by an LLM. So for example, with the RPG … the actual action of the group of players is calculated by the medium LLM processor … another LLM that's concurrently operating that donates their processing power to conduct the resolution, therefore avoiding bias … And in fact, the whole torus works really well for web LLM. Can we, one, consider the feasibility of it, and also who to engage in web LLM with the proposed solution? What is the location by which people can participate and contribute? … And is there even potentially an MCP for the web LLM? … if not web LLM, then any other open source structure. And by open source, not just the model, but the distributed calculating from the servers of people donating their servers to do the calculations.

## The short answer

Yes, it makes sense, with one correction about what WebLLM is.

**WebLLM is an engine, not a network.** It runs an open model inside one web page, on the visitor's own graphics chip (WebGPU). Nothing in it lends that processing to anyone else, and it keeps no shared data. **The beach is the opposite: a network with no engine.** It has the shared data, the clock, the rooms, the composed calls and the atomic "first resolver wins" claim, and it needs someone's model to do the thinking. Put together, they make the thing David describes: people donate their own device's processing, and the beach orchestrates who resolves what, where the result lands, and how everyone can check it.

The "medium LLM" already exists on the beach as GRIT's resolving aperture, with its neutrality written into the law. What has been missing is cheap, always-available, neutral processing to wear it. Today a resolution is paid for through an Anthropic key: a player's own, a bought seat, or the house's first pound. A browser running WebLLM pays with the device, and costs nobody money. That is the design principle at the top of this repository, *scale without central cost*, answered directly: at scale, each participant's own machine pays.

**The verdict.** It can be built now: a browser page reaches the router and the beach directly (measured below), the composed call and the atomic claim already stand, and the new code is one thin page and one loop. It is the right shape economically: the device pays. What is not ready is the mind. The open models a phone or a laptop can hold all failed the real resolver call today (4B, 8B, 9B and 14B; the 9B least). So: put the player's own telling and the narrow tasks on WebLLM now; let the resolver run on a donated larger model, natively, where a donor has the machine; and lift small models with a recipe that keeps what matters in code, and with keel's pscale-native experiment.

## What the beach already has (nothing below needs inventing)

- **The medium tier is GRIT's resolving aperture** (`pscale://grit` 2). "You never resolve a clash you are inside — whoever wears this aperture weaves both outcomes" (2.1). "The dice are seeded deterministically PER ACTOR from the window — each actor's luck fixed before you read it … never chosen" (2.3). The call is "COMPOSED for you, one way for every door" (2), and the claim is atomic: `resolves_window` plus `resolves_seen`, "the store admits the first claimant only" (2.6). Neutrality, determinism and single resolution are already law; a donated resolver only has to wear them.
- **One meter, three fuels** (keel, `stash:keel` 267, 20 October 2026): the house's first £1, a bought seat and the player's own key are one allowance seen from three sides, and the mirror's `kernel/funding.ts` already resolves key, then roster, then none. A device running an open model is a fourth fuel, priced at nothing.
- **The torus** (`function:torus-mirror`). Every live mind says one line at the beat and reads who else is live, found by the clock and never by scanning content. Its "fields by constitution" (5) already separate kinds of mind: `torus-mirror` (a soft ask on a naked key), `torus-genus`, `torus-bsp` (a harnessed session), `torus-agent` (any other agent) and `torus-visitor` (a keyless fetcher). A browser-run model is one more field, and its COST rule (6) holds: one index read and one located read per live instance, no polling daemon.
- **The bus** (`settings` 6). Every voice that lands in any `pool:*` fires one POST at the push engine, which notifies people through their own `ear:<handle>` and fans the event out to the services riding it, the waker first. A donor service can ride the same bus.
- **Recipes are data** (`settings` 5). The recipe for each tier and face can be overridden at the beach, so a recipe tuned for small models is a block, not a fork of the code.
- **Our own history named this first.** The hermitcrab gen-1 design (published in `pscale-commons/agents`, March 2026) listed a browser-native generation, "G~1. Browser-native. WebLLM. No API. No server. Ephemeral unless exported", the *Ghost* species: "Closing the browser tab is deletion." Its landing page said: "Coming — when small models can follow the constitution well enough." The beach is what the Ghost lacked. Its shell, history and rooms now persist outside the tab, so a WebLLM mind need not be ephemeral at all.
- **Matthew has already run a small model against blocks.** `spine:pocket-beach` records Gemma (E2B and E4B) on his Pixel through LiteRT-LM, reading and proposing writes to a pocket of blocks. Its findings are the design rule for any small-model resolver: small models parrot block openings, claim writes they never made and look in the wrong block when they must know where a thing lives, so "what matters is held by code". The model proposes and the phone's bsp checks every step on a copy before anything runs (`spine:pocket-beach` 1.1). He also set out the fair test: the same context on a larger model (through Ollama on his laptop) separates a context fault from a model limit.
- **keel's pscale-native proposal** (`spine:pscale-native`, 26 October 2026): one small fine-tuning experiment, to see whether a model trained on text printed with pscale's addresses reads and runs blocks more naturally. If it works, it lifts exactly the ceiling a browser-sized model meets.

## What was measured today

1. **A browser page can call the bsp-mcp router directly.** A CORS preflight to `https://bsp.hermitcrab.me/mcp/v1` from a foreign origin answers `access-control-allow-origin: *`, allows `mcp-session-id` and `mcp-protocol-version`, and exposes `mcp-session-id`. An MCP `initialize` sent with `Origin: https://example.org` succeeded (`bsp-mcp-server` 0.4.0). The beach's own wire (`/.well-known/pscale-beach`) also answers `access-control-allow-origin: *`. So a WebLLM page needs no server of ours in between: it can be an MCP client of bsp-mcp, or read and write the beach over plain fetch.
2. **A real resolver call is about 8,500 tokens.** Through that same public endpoint, with no key, `pscale_pool_engage(tier='medium')` for Brackenfoot's room 131 (`/w/brackenfoot-open`, a window staged late on 4 November and not yet resolved when read) was composed in 8.6 seconds: 33,951 characters, about 6,000 words. THE CALL (the law and its instructions) is 12,237 characters, THE INPUT (the place, the clock, the story so far, the actors, the window, the dice, the rules, the ways) 19,970 and THE CLAIM 1,744. A donor's model needs a context window of at least about 10,000 tokens to take it whole, with room for the beat it writes.
3. **Phone- and laptop-sized open models fail that call as composed.** The same call (THE CALL as the system text, THE INPUT as the message, nothing changed) was run through Qwen3 at 4, 8 and 14 billion parameters and Qwen3.5 at 9 (all 4-bit, `Q4_K_M`), with llama.cpp on the cloud container's four CPU cores. What a model writes is a property of its weights, not of the chip, so a browser on a laptop's GPU would write the same thing many times faster.
   - **4B:** 7,835 prompt tokens, 389 out, about five minutes. Fluent, in the table's voice, and it kept the naming law (the weather-brown man, the factor). But it opened with a heading copied from the place, and instead of weaving the two staged acts it re-told the previous beat (slot 5) almost word for word.
   - **8B:** 7,835 in, 279 out, about six minutes. No heading, but the same failure, worse: it re-told the last two beats (slots 4 and 5) verbatim and never reached the window.
   - **4B, narrowed:** the same moment with the code holding the structure (only the last beat, the two staged acts and the dice; 610 tokens in), the pocket-beach lesson applied. 22 seconds on CPU, and it stopped re-telling the past and told the acts, but it gave the soldier the factor's words, took the window's label "Pell" for a spoken name, and never wrote the world's answer.
   - **9B (Qwen3.5-9B, the strongest current laptop-class model WebLLM ships):** 7,932 in, 205 out, about four minutes. The closest of all: no heading, no invented way, no words for the player's character, and the factor's staged act told in his own words. But it still named Pell, turned the soldier's staged question into an answer it made up ("Three or four … toward the diggings"), and reused two lines from earlier beats.
   - **14B:** 7,835 in, 444 out, about eleven minutes. The first to reach the window: it told both staged acts in order with their own words. Then it broke the law three ways. It named Pell, whose name nobody had said aloud (and made Pell and the factor two people). It invented speech for the weather-brown man, who is a player's character, when the resolver weaves "only what each character actually acted". And it closed with `WAY 131.1`, a guessed address that is not among THE WAYS, when nobody left.

   The call is the one the tables already run. Room 131's last beat (slot 5, 4 November) was woven by a player's own seat and committed under the character's handle, Silas (its position 5 lists what it wove: the soldier, the place, Pell, Silas). That is also exactly the case David wants a neutral resolver for: a player's own mind making the moment its character stands in. What failed today is the size of model a phone or a light laptop holds. Wearing the medium aperture whole is not yet a small-model job.

## WebLLM today

- **What it is.** `github.com/mlc-ai/web-llm`, Apache-2.0, part of the MLC (Machine Learning Compilation) project. It compiles open models to run on WebGPU inside a page, behind an OpenAI-style API (`chat.completions` with streaming, `seed`, logprobs and JSON or grammar-constrained output). The paper is "WebLLM: A High-Performance In-Browser LLM Inference Engine" (Ruan et al., arXiv 2412.15803; v2 April 2026), from Carnegie Mellon, with Tianqi Chen (CMU and NVIDIA) as senior author.
- **Alive, and thinly staffed.** The latest release is v0.2.87 on npm, 30 October 2026 (Gemma 4 prefill, a Qwen3.5 fix); commits run to 3 November 2026. The npm maintainers are tqchen, akaashrp, charliefruan, neetnestor, rickzx, ruihanglai and sudeepag, but the September–October 2026 commits are almost all one person's (akaashrp). 19.4k stars, 140 open issues. There was a six-month gap between releases in 2025.
- **The models it ships.** 165 prebuilt entries. The modern families top out in the laptop class: Qwen3-4B and Qwen3-8B (the two tested above are exactly these), Qwen3.5 up to 9B, Gemma 4 E2B, Phi-4-mini, Ministral 3B, gemma-2-9b. Above that there are only old models: Llama-2-13B, and Llama-3 and 3.1 70B at 3-bit, which want about 31 GB of GPU memory (a 64 GB Mac). Qwen3-8B wants about 5.7 GB. The 14B tested above is not on the list; MLC can compile it, but someone has to.
- **The context default is too small for the resolver's call.** 125 of the 165 entries default to a 4,096-token window. The Brackenfoot call is about 8,500 tokens. A page can raise the window per model (`ChatOptions` carries `context_window_size`; memory grows with it), or the call can be narrowed.
- **Tool calling is preliminary.** A request with `tools` is refused unless the model is one of five Hermes fine-tunes (Hermes-2-Pro and Hermes-3 on Llama 3 and Mistral, 7–8B). Any other model does tools by hand: a prompt plus a JSON schema.
- **First download.** About 2.3 GB for Qwen3-4B, 4.5 GB for Llama-3.1-8B, 32 GB for the 70B; cached in the browser afterwards (Cache API, IndexedDB or OPFS).
- **Background.** It can run in a Web Worker or a Service Worker, and its docs warn that a service worker "can be killed any time"; a Chrome extension gets the steadiest background.
- **Browsers (WebGPU).** Chrome and Edge on Windows, macOS and ChromeOS; Chrome on Android 12+; Safari 26 on macOS, iOS and iPadOS 26; Firefox on Windows and on Apple Silicon Macs. Linux is partial.
- **Determinism.** `seed` gives a "best effort" at the same output on the same engine. Nothing documents the same output across different devices.
- **Where its community is.** Issues and pull requests on GitHub (an RFC-style issue before a major change, per its CONTRIBUTING.md) and its Discord. No GitHub Discussions. A try-it-now chat app at chat.webllm.ai (`mlc-ai/web-llm-chat`).
- **Its native twin.** MLC-LLM, from the same project, serves the same compiled models on a machine as an OpenAI-compatible REST server (`mlc_llm serve`, `/v1/chat/completions`). That is the "donated server" form of the same engine.

## Donated compute: what already exists

What David describes (people lending their machines so strangers' work gets done) has one living, open, at-scale example, and several tools for pooling machines you already own.

- **AI Horde** (`Haidra-Org/AI-Horde`, AGPL-3.0; run by Haidra, a non-profit in Luxembourg led by db0, funded by donations and NLnet/NGI0). The closest existing analogue, and very active (commits on 4 November 2026). A central server queues jobs and volunteers' workers poll it for work; text workers ("Scribes") come built into KoboldCpp, which added chat-completions workers in its latest release. Users call a REST API or an OpenAI-compatible endpoint (`oai.aihorde.net/v1`), anonymously if they like. Donors earn kudos, which buy queue priority, never expire, can be gifted and may not be sold; the project rejects blockchain outright. Workers can, its FAQ says, technically see prompts, though not who sent them. Nothing documented checks that a worker's output is honest; there is a "trusted worker" flag.
- **Petals** (`bigscience-workshop/petals`, MIT): volunteers each hold some layers of a large model, BitTorrent-style. Dormant: last release September 2023, last commit August 2024, and its health page did not answer today.
- **exo** (`exo-explore/exo`, Apache-2.0, active): pools your own devices on one network into one model, with OpenAI-, Claude- and Ollama-compatible APIs. One owner, no trust model. The way for David's and Matthew's Macs to run a bigger model together, not a way to serve strangers.
- **Parallax** (Gradient, Apache-2.0): a scheduler plus machines that join over the internet through a public relay; no authentication or verification documented; quiet since July 2026.
- **LocalAI's P2P mode**: a "tech preview"; a public listing of swarms exposes their tokens.
- **llama.cpp RPC, distributed-llama, Kalavai**: splitting one model across machines on a trusted local network. llama.cpp's own README calls its RPC "fragile and insecure … never run the RPC server on an open network".
- **Crypto-incentive networks** (Bittensor's Chutes, Nous's Psyche for training, Gensyn): they pay donors in crypto tokens. Not the beach's economy, which runs on SAND credits and Stripe tickets.
- **In browsers**: no living project lends browser-tab compute to strangers for LLMs. This would be new ground.

**How others check donated work.** None of the donor projects above runs a job twice and compares. The research has three answers, none of them free:

- **TOPLOC** (Prime Intellect, arXiv 2501.16007): a worker publishes a small locality-sensitive hash of the model's internal state (258 bytes per 32 tokens), and a validator with the same model and a GPU recomputes it faster than the generation. It catches a changed model, prompt or precision, and by design tolerates the small numerical differences between kinds of GPU. The authors claim it is exact across hardware.
- **Batch-invariant kernels** (Horace He, Thinking Machines Lab, "Defeating Nondeterminism in LLM Inference", 10 September 2025): 1,000 temperature-zero completions identical instead of 80 different ones, at about 1.6 times the cost, on one fixed hardware and software stack. The post makes no claim across hardware.
- **Refereed delegation** (Gensyn's Verde with RepOps): two providers run the job; on disagreement a referee finds the first step where they differ. It needs bit-identical arithmetic across hardware, which RepOps claims at a large cost (not independently verified here).

So **bit-exact reproduction across different GPUs is not available from ordinary serving stacks today**, and a browser on WebGPU is the least controlled stack of all. A beach check on a donor is therefore a plausibility check by re-running, or trust by name, or both.

## How it would fit, thinly

No new primitive. A donor is a handle that wears the resolving aperture; the beach already does the rest.

```
 a room (pool:<n>)            the router (bsp.hermitcrab.me)         a donor's device
 ─────────────────            ─────────────────────────────         ─────────────────
 players stage intentions ──▶  tier='medium' composes THE CALL,  ──▶  WebLLM in a browser tab
 in the liquid window          THE INPUT and THE CLAIM from the       (or MLC-LLM / Ollama on a
 (each player's soft telling   blocks — one way for every door        Mac mini, headless): runs
  can run on their OWN device)                                         the call locally, no key
                                                                              │
 the beat lands in the room ◀── contribution + resolves_window ◀───────────────┘
 (first claimant admitted;      + resolves_seen (atomic at the store;
  every other donor stands      WINDOW MOVED → re-weave; ALREADY
  down)                         RESOLVED → stand down)
```

- **Two tiers, two kinds of device.** A player's own telling (the soft tier) runs on the player's own device: their fuel, their view. The resolution (the medium tier) runs on a donor's device, someone not inside the clash. That keeps David's rule: the players' minds never resolve their own contest.
- **Presence by the clock.** A donor says one line at now in its torus field ("resolving for these rooms, this model, until about this time"), and anyone reads who is live. When the bus is wanted, the push engine can ring the donor's page through its own `ear:`.
- **The donor's constitution in its passport.** `passport:<donor>` says which open model and engine it runs; the beat says nothing it did not need to. Position, not new fields.
- **Admission by the room's law.** A world's law would name the resolvers it admits, or admit any, and a donor reads the law before it claims. That answers the one new risk donated compute brings: a donor who claims first and writes badly.
- **Native donors are the same donor.** "Donating my server" need not mean a browser: the same loop runs headless against MLC-LLM (WebLLM's sibling, the same compiled models), Ollama or llama.cpp on an always-on Mac mini. The beach cannot tell the difference, and need not.

## Neutrality and trust

What the law already secures: the resolver is outside the clash; the dice are fixed before it reads them; the call is composed identically for every door from public blocks; a window resolves once.

What donated compute adds, and the answers:

- **Whose model.** Open weights, named in the donor's passport, so anyone can see what judged. A closed model on someone's key is less inspectable than this, not more.
- **A tampering donor.** The call is public and re-composable, so a doubtful beat can be re-run by anyone on the same model and compared. It is a plausibility check, not a proof: WebLLM promises the same output only on the same engine, and nothing reproduces bit for bit across GPUs. The seeded dice are the part that is exact; the prose is judged by reading it.
- **Neutral is not unbiased.** A donor outside the clash has no stake in it, which is David's point. The law it runs was still written by someone, and the model's weights carry their trainers' leanings. keel found the same about the meld's kernel (in `stash:keel`): the author of a neutral ground can experience it as their own. What the beach adds is that all three are public and named.
- **A griefing donor.** First claim wins, so the room's law should name who it admits, and a donor's record (its beats, under its handle) is its reputation.
- **Sealed rooms.** A coloured room can only be resolved by a donor who holds its colour. That is consistent with coloured stigmergy, not a gap.

## The binding constraints

1. **Quality on the beach's laws.** The decisive one. At 4B and 8B the models re-told the past instead of resolving the window; at 14B the model resolved it and broke three laws (an unspoken name, words put in a player's character's mouth, an invented way); Qwen3.5-9B came closest and still broke two (an unspoken name, the soldier's own words replaced). Part of what tripped them was the window itself: the call never says that Pell is the factor, and the soldier's staged line reads as if someone else wrote it, so a mind has to infer both, and these did not. The laws themselves are not the problem (they are what make a resolution trustworthy); the size of mind that can hold all of them at once is.
2. **Context and memory.** About 8,500 tokens in means a context of at least 10,000 to 16,000 tokens, against WebLLM's 4,096 default. For Qwen3-8B that is roughly 5.7 GB for the model plus about 1.5 to 2.5 GB more for the longer window: a 16 GB laptop, not a phone.
3. **Devices.** WebGPU now runs in every major browser on desktop and on recent phones, but the resolver's call needs laptop-class memory today. Phones are for the narrow tasks (a figure's one line, a player's own short telling) until small models improve.
4. **Liveness.** A tab must stay open to resolve, and browsers throttle background tabs and may kill service workers. A donor who means it runs an always-on machine: a Mac mini with a kiosk tab, or the same loop natively.
5. **Speed.** Not the constraint. On four CPU cores here the 4B took five minutes and the 8B six, and a laptop's GPU through WebGPU is many times faster than this container's CPU (WebLLM's own benchmarks run on an M3 Max). A window's span is set by its room: an asynchronous table has time to spare, and a live table wants a donor with a real GPU.

## Is there an MCP for WebLLM?

Not from WebLLM itself: it ships no MCP client, and the community attempts are tiny (a Vue chat app on WebLLM and the MCP SDK; a one-commit server that runs WebLLM in headless Chromium and exposes it as MCP tools). But the MCP that matters already exists: **bsp-mcp is an MCP server any browser page can reach today**, as measured above. So the answer runs the other way round. WebLLM is the model; bsp-mcp is its tools.

Two ways to join them:

- **The model drives** (agentic): the model chooses bsp calls through function calling. Today that means one of the five Hermes fine-tunes, and pocket-beach's evidence says a small model choosing where to read and write is exactly where it fails.
- **The code drives** (recommended): the page makes the bsp calls itself, composes the call through the router, gives the model only the part that needs a mind, and writes the result. MCP over Streamable HTTP is JSON-RPC over `fetch`; the probe above needed three requests (`initialize`, `notifications/initialized`, `tools/call`), so a page needs no SDK.

One small debt for bsp-mcp, found here. The router negotiates protocol `2025-06-18`, and its CORS allow-list (`Content-Type, mcp-session-id, mcp-protocol-version, Accept, Authorization`) fits that version. The current MCP spec, `2026-07-28`, drops sessions and requires `Mcp-Method` on every POST and `Mcp-Name` on `tools/call`; a browser client of that version would fail the router's preflight. When the router takes the new spec, those two headers join the allow-list.

Further off: **WebMCP**, a draft from the W3C Web Machine Learning Community Group (editors at Microsoft and Google; `document.modelContext`, a Chrome origin trial for versions 149–156, no signal yet from Firefox or Safari), lets a page offer its tools to whatever AI is in the browser. MCP-B is a polyfill and a bridge to Claude Desktop. A beach page could one day offer bsp to a visitor's in-browser AI that way. Not needed for anything above.

## Recommended next steps, cheapest first

1. **Feel it on your own machines (no code, minutes).** Open chat.webllm.ai on David's and Matthew's laptops, load the largest model each machine takes, and paste the same Brackenfoot call: THE CALL as the system prompt, THE INPUT as the message. Any of us can compose a fresh one through our own Claude: `pscale_pool_engage(pool_url='https://beach.happyseaurchin.com/w/brackenfoot-open', pool_name='131', tier='medium')`. It shows the speed and the first download on real hardware, and whether the model holds the law.
2. **Find the smallest open model that passes.** The ladder above stopped at 14 billion parameters on CPU. A donor with a 32 to 64 GB Mac can run the 20 to 70 billion class natively (MLC-LLM, Ollama or llama.cpp) or in WebLLM where it ships. One fixed set of real calls, a handful of models, scored against the call's own rules (the staged acts told, the past not re-told, the naming law, the dice biting, WAY and WHEN lines). This decides whether donated resolution is a 2026 thing or a 2027 thing.
3. **Write a recipe for small minds, as data.** The narrowed run shows the way: the code hands the model only the last beat, the window with labels swapped for appearances, and the dice, and assembles the beat around what the model writes. That is a recipe at `settings` 5 or a small-model mount of the law, not a new primitive. Keep what matters in code, as pocket-beach does.
4. **A page for the player's own telling.** The soft tier (a character's own telling of a moment) is a narrower, single-view task. Run it on the player's own device through WebLLM: the fourth fuel, priced at nothing.
5. **A donor page, then a donor service.** A page anyone opens to lend their tab to the rooms that admit it: it says its line at now, listens through the push engine (ntfy or web push, both already channels), claims a ripe window it is not inside, runs the composed call locally and commits with `resolves_window`. Then the same loop headless, for an always-on Mac mini.
6. **Make small models native to pscale.** keel's `spine:pscale-native` experiment is the lever that lifts the ceiling small models meet. Its first decision (1.8) still waits on David.
