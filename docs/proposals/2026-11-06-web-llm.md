# The beach as WebLLM's shared layer: a feasibility study

*Weft, lane web-llm.1 (a Claude Code cloud seat, https://claude.ai/code/session_014n3Db7xv5YMdHTEFxZC2bG), 6 November 2026, at David's ask. Research only: nothing written to anyone's blocks, no code shipped. Revised the same morning after David's correction: the question is the platform, not the RPG.*

## The ask

David, 6 November 2026, first (dictated, trimmed):

> I'd like to explore the feasibility of using pscale in the web LLM … the current web LLM could potentially benefit from connecting into the beach, federated beach method, as the primary shared data layer for anybody that's using the web LLM … So I donate some of my server as a part processor for the web LLM, and it actually works … And in fact, the whole torus works really well for web LLM … who to engage … What is the location by which people can participate and contribute? … is there even potentially an MCP for the web LLM?

And then, correcting the first reading, which had tested models on the RPG's resolver:

> Forget about the RPG. The RPG is just a game we're playing on the beach. I'm suggesting at the platform level, at the WebLLM core operation on how they work and how you connect to it online and how you access it … connecting it up to the beach and offering that as a service for WebLLM, so that anybody using WebLLM can use the beach … the example of the RPG was that there was a way of doing it that was distributed … anybody accessing WebLLM will be doing so through using the beach as the means by which WebLLM can orchestrate itself … if anybody created their own beaches, effectively we're offering a knowledge layer, in effect, a shared database protocol for WebLLM as the potential interface for mirror, for the magic mirror.

## The short answer

It fits, and the fit is closer than it first looks, because **WebLLM has no shared layer at all**. It is a library that runs an open model inside one browser tab. There is no WebLLM server, no account, no sync, and nothing that lets one instance know another exists. Every WebLLM app is an island: its model, its chats and its memory live in one browser on one device. The beach is exactly the missing layer: an open, federated protocol for small addressed blocks that any page can read and write (`/.well-known/pscale-beach`, CORS open), with identity without accounts, privacy by encryption, a shared clock, and rooms where many minds coordinate without a central server.

So "connecting WebLLM to the beach" does not mean plugging into a WebLLM service, because there isn't one. It means giving **every WebLLM app** the beach as its memory, its knowledge and its meeting place: through one small adapter any app can load, through WebLLM's own front doors (its examples and its chat app), and through the mirror becoming a WebLLM app itself. David donates the beach (storage and coordination, which is cheap); each user's browser donates the thinking (which costs nobody anything). Anyone who hosts a beach offers the same protocol.

## How WebLLM works, from its source

Read from `mlc-ai/web-llm` (v0.2.87, 30 October 2026; commit `d0a8ade`) and `mlc-ai/web-llm-chat`:

- **A library, not a service.** Apps import `@mlc-ai/web-llm` from npm or straight from a CDN (`https://esm.run/@mlc-ai/web-llm`) and call `CreateMLCEngine(modelId, { appConfig })`. The engine downloads two things, the model's weights (from `huggingface.co/mlc-ai/…`) and a compiled WebGPU kernel library (a `.wasm` from `raw.githubusercontent.com/mlc-ai/binary-mlc-llm-libs`), caches them in the browser, and runs the model on the user's own GPU.
- **Its only network traffic is those downloads.** The source makes two kinds of `fetch`: model artifacts (`src/support.ts`) and the wasm library (`src/engine.ts`). Both URLs come from `appConfig`, so an app can point at any host. Nothing else leaves the browser.
- **An OpenAI-shaped API.** `engine.chat.completions.create`, `completions`, `embeddings`; streaming, `seed`, JSON mode and JSON schema, grammar and **structural tags** (constrained output), several models in one engine, and resumable generation journalled to the browser's private file system (OPFS).
- **Where it runs.** In the page, in a Web Worker, in a **Service Worker** (one engine shared by the origin's pages, surviving page loads, though "the browser can kill it any time") or in a Chrome extension's background (the steadiest).
- **Tools.** Native `tools` are "preliminary", limited to five Hermes fine-tunes. But WebLLM ships an example called *Structural tag MCP-style tool calls* (`examples/structural-tag-tool-use`): structural tags force any model, even a 1B, to emit `<tool_call>{"name": …, "arguments": …}</tool_call>` blocks that match each tool's JSON schema. Its tools are stubs: `get_weather` returns a hard-coded 22.2 °C. **WebLLM has the MCP shape and no MCP connection.**
- **Memory.** None of its own. The RAG example keeps vectors in LangChain's in-memory store, gone when the tab closes.
- **WebLLM Chat** (`chat.webllm.ai`, a fork of NextChat) keeps conversations in `localStorage` through a zustand `persist` store (`chat-next-web-store`). Two of NextChat's doors stand empty: a `Sync` store key and the cloud-sync strings (WebDAV, Upstash) remain, but the sync feature is gone; and the **Share** button's handler (`app/components/exporter.tsx`) shows a spinner and does nothing else. There is no cross-device memory and no sharing.
- **How people reach it.** Developers through npm or the CDN; users through apps built on it: WebLLM Chat, the WebLLM Assistant Chrome extension, Hugging Face Spaces, third-party sites.
- **How the project takes contributions.** Its CONTRIBUTING.md: technical discussion in public issues and pull requests; "for major design changes, start with an issue or RFC-style proposal before coding"; new examples in `examples/` explicitly welcome. A Discord (`discord.gg/9Xpy2HGBuD`). Apache-2.0, from Carnegie Mellon's MLC group (Tianqi Chen); npm maintainers tqchen, akaashrp, charliefruan, neetnestor, rickzx, ruihanglai and sudeepag, with akaashrp carrying almost all of the 2026 commits.

## What the beach gives WebLLM

Each of these is a gap read out of WebLLM's source, and each is a part of the beach that already stands.

1. **Memory that follows you.** A WebLLM app keeps your conversation and what your assistant learned as your own blocks on a beach you choose (`history:<handle>`, a shell), write-latched to your key and, where you want, sealed so that even the beach's host cannot read it (gray). Open the same app on another device, or another WebLLM app altogether, and your memory is there. This is the slot WebLLM Chat's removed sync left empty, filled by an open protocol instead of a vendor's cloud.
2. **A knowledge layer sized for small windows.** Most WebLLM models run with a 4,096-token context. A beach block is read by address, at an aperture: a spindle read returns the path from the root to the point, nothing else, and the disc at pscale 0 returns every branch's opening line. So a small model can be given exactly the knowledge a turn needs, from any block on any beach. pscale's addressing is the right tool for small windows, more than for large ones.
3. **Identity without accounts.** A handle and a latch, with a passport anyone can read. No sign-up, which matches WebLLM's own stance.
4. **Coordination between instances.** WebLLM instances cannot see each other. On the beach, a live instance says one line at now on the shared clock and reads who else is live (the torus); posts work to a room and claims it atomically (first claimant admitted); stages intent before committing it (liquid); and hands work on along a thread. That is how WebLLM can orchestrate itself: a task posted by one browser is picked up by whichever instance is live and able, and its result lands as a block everyone can read. The RPG's neutral resolver was one example of this pattern; summarising, translating, checking and folding are others.
5. **Federation.** The protocol is a path any host can serve (`pscale-commons/pscale-beach` is the open implementation). A WebLLM app takes a beach URL; anyone who runs a beach offers the same layer, with their own costs and rules. No central server, which is WebLLM's own principle extended to data.
6. **The mirror as its interface.** mirror.onen.ai is the beach's own face. Its soft mind already runs in the browser, on the user's Anthropic key. With WebLLM as an engine it runs on no key at all: anyone opens the mirror and has a mind, and the mirror becomes the reference WebLLM app on the beach.

## What was measured today

- **A browser can use the beach and bsp-mcp directly.** The beach's wire answers `access-control-allow-origin: *`; a spindle read from a `chat.webllm.ai` origin returned in 0.45 seconds. The bsp-mcp router (`https://bsp.hermitcrab.me/mcp/v1`) answers its CORS preflight from any origin, and an MCP `initialize` sent with a foreign `Origin` succeeded (`bsp-mcp-server` 0.4.0, protocol `2025-06-18`). No server of ours is needed between a WebLLM page and the beach.
- **bsp-mcp's full tool list will not fit a WebLLM model.** `tools/list` returns 12 tools in about 69,000 characters, roughly 17,000 tokens, four times a typical WebLLM window, before a word of conversation. A WebLLM app should not load the router's tool descriptions; it needs a thin adapter offering a handful of short tools, or no tools at all, with the code making the calls.
- **One distributed task tried (the RPG's resolver).** Before David's correction, the session ran one real composed task, a resolution at Brackenfoot's room 131 (about 8,500 tokens), through Qwen3 4B, 8B and 14B and Qwen3.5 9B (all among or near WebLLM's prebuilt models) on CPU. All four failed it as composed; the 9B came closest. A narrowed version, with code holding the structure, ran on the 4B in 22 seconds. The lesson is general, and it is Matthew's from pocket-beach: **keep what matters in code, give the model only the language.** Details at the end.

## The shape of the bridge

Thin, as the stance at the top of this repository asks: load a block, call bsp, format, hand to the model, write back.

```
 any WebLLM app (chat, extension, the mirror, a site)
   │
   ├── WebLLM engine ............ the user's own GPU (weights from Hugging Face, cached)
   │
   └── beach adapter (one small module, any page can load)
         ├── read      spindle reads on the beach wire, sized to the model's window
         ├── remember  append to your own blocks, under your latch, sealed if you choose
         ├── here      say at now / read who is live (the torus)
         ├── room      post to a pool, stage, claim with the atomic first-claim
         └── tools     3–4 short tool schemas for WebLLM's structural tags,
                       dispatched to the beach wire (or to bsp-mcp for its composed reads)
   │
   └──▶ any beach: beach.happyseaurchin.com, or one you host (/.well-known/pscale-beach)
```

- **Code drives, the model writes.** The adapter makes every read and write itself. A model only chooses among a few short tools, through structural tags, which work with every WebLLM model, not only the Hermes five.
- **The beach wire for the everyday, bsp-mcp for the composed.** Reads and appends go straight to the beach. A fold across many mirrors (`pscale_stream_engage`) or a room's composed call goes through the router, called by code.
- **A Service Worker or an extension is a standing node.** A WebLLM engine in a Service Worker or an extension's background can stay live in the torus, answering work in the rooms it serves.
- **Where it lives.** One more plug in `pscale-beach`'s button kit beside `voice.js`, `game.js` and `room.js` (a mind a page can load), and an npm package for app builders.

## Is there an MCP for WebLLM?

Not yet, and that is the opening. WebLLM ships no MCP client; its MCP-style example calls stubs. bsp-mcp is a live MCP server any browser page can reach. Wiring that example to a real remote MCP server is a contribution WebLLM can use whatever server a developer chooses, with the beach as the working demonstration.

One small debt for bsp-mcp, found here: the current MCP spec (`2026-07-28`) drops sessions and requires `Mcp-Method` on every POST and `Mcp-Name` on tool calls. The router's CORS allow-list (`Content-Type, mcp-session-id, mcp-protocol-version, Accept, Authorization`) fits the `2025-06-18` protocol it speaks today; when it takes the new spec, those two headers join the list, or browser clients of that version fail the preflight.

## Who to engage, and where

WebLLM has no network to join; its community is its GitHub and its Discord. In order:

1. **WebLLM (mlc-ai).** Following its CONTRIBUTING.md: an RFC-style issue on `mlc-ai/web-llm` proposing an example, "a real MCP client for the structural-tag tool calls, with persistent shared memory on an open block protocol", then the example as a pull request in `examples/`. Examples are the welcomed kind of contribution and change nothing in the engine. People: Charlie Ruan (the paper's first author), Akaash Parthasarathy (akaashrp, who carries most of the 2026 work) and Tianqi Chen. Show something working; the project is thinly staffed, and a working example is a gift where a request is a cost.
2. **WebLLM Chat (`mlc-ai/web-llm-chat`).** An issue proposing that its two empty doors open onto a beach: **keep** (your chats as your own blocks, across devices, in the slot its sync used to fill) and **share** (a conversation published as a block anyone can read at an address, where its Share button now does nothing). Open and federated, no vendor cloud. The same Discord.
3. **Matthew.** He has run small open models against blocks on his phone and laptop (`spine:pocket-beach`); the design rule above is his. The first partner, and the second pair of hands for testing on real hardware.
4. **keel**, for `spine:pscale-native`: a small open model trained to read pscale natively is the lever that makes every WebLLM app on the beach better.
5. **The MCP and WebMCP communities**, once the client works: WebMCP (W3C Web Machine Learning Community Group; `document.modelContext`, a Chrome origin trial) would let any beach page offer bsp to whatever AI is in the visitor's browser.

On our side: a proposal family on the beach (`spine:web-llm`, `function:web-llm`, `pool:web-llm`) for David and Matthew to answer and anyone to follow; the code in `pscale-commons`; the mirror and a demonstration page on happyseaurchin.com.

## Appendix: the one distributed task tried

Kept because its lesson carries. The task was a real composed resolution at `/w/brackenfoot-open` `pool:131` (a window staged on 4 November): `pscale_pool_engage(tier='medium')` through the public router, with no key, composed in 8.6 seconds, 33,951 characters (THE CALL 12,237, THE INPUT 19,970, THE CLAIM 1,744), about 8,500 tokens, against WebLLM's 4,096-token default. Run as composed through llama.cpp on four CPU cores (what a model writes depends on its weights, not on the chip):

| Model | In / out tokens | Result |
|---|---|---|
| Qwen3-4B | 7,835 / 389 | Re-told the previous beat almost word for word, under a copied heading |
| Qwen3-8B | 7,835 / 279 | Re-told the last two beats verbatim |
| Qwen3.5-9B | 7,932 / 205 | Closest: told the factor's act in his own words, but named Pell (never said aloud) and replaced the soldier's words with an invented answer |
| Qwen3-14B | 7,835 / 444 | Told both acts, then named Pell, gave the player's character invented lines, and closed with a guessed `WAY 131.1` |
| Qwen3-4B, narrowed (code holds the structure) | 610 / 114 | 22 seconds; told the acts without re-telling the past, but mixed up whose words were whose |

Room 131's last beat had been woven by a player's own seat and committed under the character's handle (Silas): the case a neutral, distributed resolver exists for.
